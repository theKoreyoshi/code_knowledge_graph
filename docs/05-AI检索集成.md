# AI 修改代码时调用知识图谱

本工具的 AI 集成采用“图谱先定位，源码再取证”的方式：

```text
用户修改请求
    -> search_code_symbols
    -> get_code_context
    -> AI 修改源码
    -> analyze_change_impact
    -> 编译 / 测试 / 重建图谱
```

知识图谱是导航和影响分析层，源码仍然是最终事实来源。AI 不应直接读取整个工程。

## 1. 生成图谱

```bash
python -m ckg build D:/work/driver -o D:/work/driver/ckg-out
```

图谱输出目录至少需要 `entity.json`、`relation.json` 和 `run_meta.json`。

## 2. 查询 AI 上下文

```bash
python -m ckg context App_Run ^
  -d D:/work/driver/ckg-out ^
  --depth 1 --max-files 8 --max-lines 400 --format json
```

返回目标实体、关系、源码范围、带行号的源码文本，以及
`external`、`dead_code`、`low_confidence` 等警告。

`--depth` 是图谱遍历深度，不代表读取整个工程。`--max-files` 和
`--max-lines` 是上下文硬限制，适合直接作为 AI 工具预算。

## 3. 分析修改影响

```bash
python -m ckg impact App_Run ^
  -d D:/work/driver/ckg-out --depth 2 --format json
```

影响分析返回直接调用者、直接被调用者、受影响实体和文件、风险等级及原因。
它不依赖某个驱动框架，判断只使用实体类型、关系类型、文件后缀、调用数量和
解析质量，因此适用于裸机、RTOS、Linux 驱动和普通 C/C++ 工程。

## 4. Agent 工具接口

`ckg.agent_tools` 提供与 AI 厂商无关的工具定义和分发函数：

```python
from ckg.agent_tools import dispatch_tool

result = dispatch_tool(
    "get_code_context",
    {"symbol": "App_Run", "depth": 1, "max_lines": 400},
    graph_dir=r"D:/work/driver/ckg-out",
)
```

支持的工具：

| 工具 | 用途 |
|---|---|
| `search_code_symbols` | 根据名称查函数、类型、变量、宏或文件 |
| `get_code_context` | 返回受限图谱上下文和源码范围 |
| `analyze_change_impact` | 返回影响实体、文件和风险 |

工具定义可以通过命令导出，供 MCP、OpenAI Function Calling、IDE Agent 或
自研 Agent 注册：

```bash
python -m ckg tools
```

宿主收到 AI 工具调用后，把工具名、参数和图谱目录传给
`dispatch_tool()` 即可。检索逻辑不依赖具体模型或 IDE。

## 5. 接入 MCP 服务

本项目内置了一个依赖无关的 MCP `stdio` 服务。它不监听端口，而是由 MCP
客户端启动子进程，通过标准输入输出传输 JSON-RPC 消息。

### 手动启动

```bash
python -m ckg.mcp_server --graph-dir D:/work/driver/ckg-out
```

也可以使用安装后的命令：

```bash
ckg-mcp --graph-dir D:/work/driver/ckg-out
```

Windows 下建议在客户端配置中填写 Python 的绝对路径和模块参数，例如：

```json
{
  "mcpServers": {
    "code-kg": {
      "command": "C:\\Python311\\python.exe",
      "args": [
        "-m",
        "ckg.mcp_server",
        "--graph-dir",
        "D:\\work\\driver\\ckg-out"
      ]
    }
  }
}
```

如果 `ckg` 已安装到当前环境，也可以配置：

```json
{
  "mcpServers": {
    "code-kg": {
      "command": "ckg-mcp",
      "args": ["--graph-dir", "D:\\work\\driver\\ckg-out"]
    }
  }
}
```

不同 MCP 客户端的配置文件位置不同，但 `command` 和 `args` 的含义相同。
配置完成后重启客户端，它应能发现以下工具：

| MCP 工具 | 用途 |
|---|---|
| `search_code_symbols` | 查找函数、类型、变量、宏或文件 |
| `get_code_context` | 获取受限图谱上下文和源码片段 |
| `analyze_change_impact` | 获取修改影响范围和风险 |

### 启动前提

必须先完成一次图谱构建，且 `--graph-dir` 下存在：

```text
entity.json
relation.json
run_meta.json
```

MCP 服务只负责读取图谱和源码，不会自动修改代码，也不会自动重建图谱。
AI 修改完成后建议执行：

```text
重新 ckg build
-> 再调用 get_code_context / analyze_change_impact
-> 编译和运行测试
```

### 通信和排错

MCP 服务的标准输出专门用于 JSON-RPC，不能在 stdout 打印日志。启动错误会
写入 stderr。常见问题：

- 客户端看不到工具：检查 `command` 是否指向安装了 `code-kg` 依赖的 Python；
- 找不到图谱：检查 `--graph-dir` 是否直接包含 `entity.json`；
- 源码片段为空：检查 `run_meta.json` 的 `source_root` 是否仍然有效；
- 图谱内容过期：重新执行 `ckg build`。

## 6. 推荐修改流程

修改函数实现：

```text
search_code_symbols("目标函数")
get_code_context("目标函数", depth=1)
修改目标函数源码
analyze_change_impact("目标函数", depth=2)
编译并运行相关测试
```

修改结构体字段时重点检查 `READS`、`WRITES`、`TYPE_OF`；修改宏时重点检查
`USES_MACRO`、`MACRO_DEPENDS_ON`、`CALLS_MACRO`；删除函数前必须检查所有
`CALLS` 入边和函数指针关系。

## 7. 图谱过期处理

源码修改后，旧图谱可能过期。第一阶段建议重新执行 `ckg build`，再执行
`context` 和 `impact`，最后编译和测试。后续可以在 `run_meta.json` 中记录
每个文件的 hash，只重新解析变化文件及其包含关系上游。

## 8. 泛化边界

静态图谱无法完全确定动态注册回调、汇编或链接脚本符号、运行时加载驱动、
复杂宏拼接和缺少完整编译参数的工程。本工具通过 `CALLS_PTR`、`ASSIGNED_TO`、
`external`、`low_confidence` 等字段暴露不确定性，Agent 应把它们作为警告。
