## 1. 这个工具做什么

输入一个 C/C++ 工程目录，输出一份**代码知识图谱**：

```
你的工程  ──►  entity.json / relation.json      （机器可读的实体与关系）
               macro_expansions.json             （每处宏展开点）
               preprocessed/*.i                  （真正编译时的代码）
               ckg.html                          （可交互浏览的图谱）
               graph.graphml                     （可导入 Gephi / Neo4j）
```

它和"正则扫一遍源码"的区别在于：解析走的是 **clang 的真实语义 AST**，
所以类型已解析、宏已展开、每个标识符都能定位到它的定义。

图谱能细到什么程度：

```c
#define unit (g_units[active_unit])

unit.speed = value;
```

普通工具看到的是"给变量 `unit` 的字段赋值"；本工具记录的是
**「函数 →WRITES→ `g_units`」+「函数 →WRITES→ `active_unit`」**，
并且这两条边带 `via_macro: "unit"` 标记 —— 即"这段代码是通过宏 `unit` 写进去的"。

## 2. 安装

### 2.1 推荐：源码 + 虚拟环境

```bash
git clone https://github.com/theKoreyoshi/code_knowledge_graph.git
cd code_knowledge_graph
python -m venv .venv

# Windows
.venv\Scripts\python -m pip install -r requirements.txt
# Linux / macOS
.venv/bin/python -m pip install -r requirements.txt
```

### 2.2 或者：装成命令

```bash
pip install -e .                 # 之后可在任意目录使用 ckg 命令
pip install -e ".[preprocess]"   # 额外安装 ziglang（提供 clang 驱动 + 完整 C/C++ 头文件）
```

### 2.3 依赖说明

| 依赖 | 是否必需 | 作用 |
| --- | --- | --- |
| `libclang` | 必需 | clang 前端库（wheel 自带 `libclang.dll` / `.so`，**不需要**装完整 LLVM） |
| `tree-sitter` + `tree-sitter-c` | 必需 | 语法层解析，预编译包，无需编译 `.so` |
| `ziglang` | 可选 | 提供 clang 驱动和完整 C/C++ 标准头文件；Windows 上最省事 |
| 系统 `clang` / `gcc` | 可选 | 若 PATH 中存在则优先使用 |

检查环境是否就绪：

```bash
python -m ckg info
```

## 3. 第一次建图

### 3.1 零配置

```bash
python -m ckg build  D:/work/myproject
```

工具会自动：

1. 找构建系统（`compile_commands.json` → CMake → Make → Meson → IAR `.ewp` → Keil `.uvprojx` → 目录扫描）；
2. 向编译器问出 include 路径与预定义宏；
3. 自动补齐缺失的头文件 / 类型 / 函数声明；
4. 用 clang 解析全部翻译单元（可并行）；
5. 展开宏、生成可视化。

实际输出：

```
[ckg] auto-detect + build: D:/work/myproject
  detected build provider: cmake
    - CMakeLists.txt
  libclang: clang version 18.1.1
  compiler driver: python -m ziglang cc
  sources: 42 translation units, 17 headers
  auto-repair round 1: +3 headers, +0 types, +0 functions, +0 variables, +0 macros
  auto-repair round 2: +0 headers, +0 types, +0 functions, +6 variables, +0 macros
  clang pass: 12.4s (42 units, 4 workers)
  diagnostics: 0 errors, 0 warnings
  clang -E pass: 42 units in 9.1s
  tree-sitter pass: 0.6s (3120 nodes checked, 12 only present in text)

  entities : 4821
  relations: 15302
  elapsed  : 24.3s
  output   : D:/work/myproject/ckg-out
```

### 3.2 常用参数

```bash
# 并行度（缺省按 CPU 自动，最多 8）
python -m ckg build D:/work/myproject -j 8

# 指定输出目录
python -m ckg build D:/work/myproject -o D:/out/mygraph

# 只要语义层，不做 tree-sitter 交叉校验（更快）
python -m ckg build D:/work/myproject --engine clang

# 跳过真实预处理（没有 clang 驱动时）
python -m ckg build D:/work/myproject --no-preprocess

# 不要自动补桩，让缺失头文件直接报错（想看清到底缺什么）
python -m ckg build D:/work/myproject --no-repair
```

### 3.3 先看看它会怎么解析

不建图，只做识别，确认 include 路径和宏定义对不对：

```bash
python -m ckg init D:/work/myproject
```

输出包含检测到的构建系统、语言、include 目录、宏定义、目标平台，以及判定依据。
加 `-o my.json` 可把这份配置落盘，作为后续手工调整的起点。

## 4. 看懂输出

默认输出目录 `<项目>/ckg-out`（用 `-o` 可改）：

| 文件 | 内容 | 怎么用 |
| --- | --- | --- |
| `entity.json` | 全部实体 | 每个实体含 `id / type / name / file / line / degree / external` 等 |
| `relation.json` | 全部关系 | 每条含 `head / tail / type / count / sites`，宏相关边还有 `via_macro` |
| `macro_expansions.json` | 宏展开点 | 字段与 `code_kg_with_tree-sitter` 的 `macro.json` 兼容 |
| `macro_expansions_detailed.json` | 展开点详情 | 多出实参、推导展开文本、`clang -E` 实际输出 |
| `preprocessed/*.i` | 真实预处理结果 | 宏全部展开后的完整代码 |
| `ckg.html` | 交互式图谱 | 双击打开 |
| `graph.graphml` | 标准图格式 | Gephi / yEd / Neo4j |
| `报告.md` | 中文分析报告 | 热点函数、宏热点、死代码、未调用函数 |
| `graph_stats.json` / `run_meta.json` | 统计与运行元信息 | 程序化读取本次运行的全部细节 |
| `_auto_shim/` | 自动生成的桩 | 缺 SDK 时生成的声明，可人工改写后重跑 |
| `_toolchain/frontend_compat.h` | 前端兼容垫片 | 处理 libc++ 版本差异、`__INT32_C` 等 |

### 4.1 实体类型

`FILE` `MACRO` `FUNCTION` `METHOD` `CLASS` `STRUCT` `UNION` `ENUM` `ENUM_CONST`
`TYPEDEF` `NAMESPACE` `VARIABLE` `LOCAL` `PARAMETER` `FIELD` `EXTERNAL`

### 4.2 关系类型

| 关系 | 含义 |
| --- | --- |
| `CONTAINS` | 文件 / 类 / 结构体 / 函数 → 其成员 |
| `INCLUDES` | `#include` 依赖（系统头文件按数量汇总进 `system_headers` 字段） |
| `CALLS` | 函数 / 方法调用，含由函数指针赋值**推导**出的调用 |
| `CALLS_PTR` | 通过函数指针变量或字段的间接调用 |
| `CALLS_MACRO` | 宏展开后产生的调用 |
| `READS` / `WRITES` | 函数读 / 写某变量、字段、局部变量、形参（变量级数据流） |
| `ASSIGNED_TO` | 赋值与函数指针绑定（支持 `dev->init = DISPATCH(usb)` 这类宏间接赋值） |
| `HAS_PARAMETER` / `HAS_VARIABLE` / `HAS_MEMBER` / `HAS_METHOD` | 形参 / 局部变量 / 字段 / 方法归属 |
| `TYPE_OF` / `RETURNS` / `TYPEDEF_OF` | 类型 / 返回类型 / 别名底层类型 |
| `INHERITS` | C++ 继承 |
| `USES_MACRO` | 使用某宏（边上带展开位置与展开文本） |
| `MACRO_DEPENDS_ON` / `MACRO_ALIAS` / `GENERATES` | 宏依赖 / 宏别名 / 宏生成的声明 |

### 4.3 可信度字段

工具不会假装什么都能解析，可疑的地方都标了出来：

| 字段 | 含义 |
| --- | --- |
| `external: true` | 来自 SDK / 标准库，不在工程源码内 |
| `auto_generated: true` | 由诊断修复自动生成的声明 |
| `dead_code: true` | 文本里存在，但预处理器没编译（`#if 0` 等） |
| `low_confidence: true` | 所在文件解析错误较多，结论需人工确认 |
| 每文件 `quality` | `full` / `partial` / `degraded` |

## 5. 打开交互式图谱

直接双击 `ckg.html`（单文件、离线、无外部依赖）。

界面速览：

| 位置 | 功能 |
| --- | --- |
| 左侧「视图预设」 | 全景 / 文件模块 / 函数调用图 / 宏依赖 / 类型结构 / 变量数据流 / 全部关系 |
| 左侧「实体类型」「关系类型」 | 逐项开关，实时过滤 |
| 顶部搜索框 | 输入函数 / 变量 / 宏名定位（`/` 聚焦，回车跳第一个命中） |
| 画布 | 滚轮缩放、拖空白平移、拖节点微调、**双击节点进入邻域隔离** |
| 右侧详情面板 | 源码原文、宏定义体、宏展开结果、`clang -E` 真实代码、全部入边出边（可点击跳转） |
| 画布右下角图例 | 颜色对照表 |

几个高效用法：

- **查"这个变量谁在改"**：切到「变量数据流」预设 → 搜索变量名 → 看 `WRITES` 入边。
- **捋宏的影响面**：切到「宏依赖与使用」预设 → 点某个宏 → 看 `USES_MACRO` 出边覆盖了哪些函数。
- **排查间接调用**：切到「函数调用图」→ 找 `CALLS_PTR`（黄色）边，再看它旁边是否已有推导出的 `CALLS`。
- **找死代码**：红虚线圈的节点即"文本存在但没参与编译"的代码。

## 6. 用配置文件精调

零配置够用时不必写配置；遇到特殊情况（私有 SDK、特殊宏、多目标平台）再写：

```jsonc
{
  "project_name": "myproj",
  "title": "myproj 代码知识图谱",
  "source_root": "D:/work/myproject",
  "output_dir": "./ckg-out",

  "include_dirs": ["inc", "vendor/sdk/include"],
  "std_shim_dirs": ["ckg/shims"],          // 标准库桩，仅在裸机目标下生效
  "shim_include_dirs": ["shims/vendor"],   // 工程专属缺失头文件的桩，始终生效

  "defines": ["USE_DMA=1", "BOARD_V2"],
  "extra_args": ["-Wno-implicit-function-declaration"],
  "std": "gnu11",                          // C++ 用 gnu++17
  "target": "arm-none-eabi",               // 裸机建议显式指定

  "compile_commands": "",                  // 留空自动查找
  "auto_repair": true,
  "excludes": ["third_party", "tests", "generated"],
  "extensions": [],                        // 留空用默认扩展名集合
  "include_globs": [],                     // 只分析匹配的文件
  "tree_sitter": true,
  "preprocess": true,
  "clang_driver": "",                      // 例："C:/Program Files/LLVM/bin/clang.exe"
  "jobs": 0                                // 0 = 自动
}
```

用法：

```bash
python -m ckg build -c myconfig.json
python -m ckg build -c myconfig.json -o D:/out/mygraph -j 8
```

### 6.1 缺失头文件怎么补

两条路，按需选：

1. **让工具自动补**（默认）：跑一次后看 `_auto_shim/`，里面是自动生成的桩头文件与
   `ckg_autodefs.h`（含合成的 typedef / 函数声明 / 变量声明）。想手工修正就编辑它，然后重跑。
2. **手工提供真实桩**：把真实头文件（或摘录）放进 `shim_include_dirs` 指向的目录。
   参考 `examples/vendor-shims/` 的写法 —— 那是给一个嵌入式工程写的驱动头文件桩。

### 6.2 目标平台怎么选

| 场景 | 建议 |
| --- | --- |
| 裸机 / RTOS（IAR、Keil、GCC ARM） | `"target": "arm-none-eabi"`，类型宽度符合 ILP32 |
| Windows 桌面程序 | 留空（用编译器默认） |
| Linux / macOS | 留空，或显式 `x86_64-linux-gnu` |
| Windows 上要解析 C++ | 无需干预，工具会自动切到 `x86_64-linux-musl` 以获得完整 libc++ |

## 7. 不同形态工程怎么处理

### 7.1 有 `compile_commands.json`（最准）

```bash
# CMake 工程先生成它
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
python -m ckg build .
```

工具会自动找到 `compile_commands.json`（根目录、`build/`、或任意一级子目录），
逐文件使用里面记录的**原始编译参数**。

### 7.2 CMake / Make / Meson

自动解析 `CMakeLists.txt` 的 `include_directories` / `target_include_directories` /
`add_definitions` / `CMAKE_C_STANDARD` / `CMAKE_CXX_STANDARD`，以及 Makefile 里的
`CFLAGS` / `CPPFLAGS` / `-I` / `-D`。

### 7.3 IAR 工程（`.ewp` / `.ewd` / `.eww`）

自动读取工程文件里的 IncludePath 与 Defines 节点，处理 `$PROJ_DIR$` 变量；
并通过源码特征（`__ICCARM__`、`IRQHandler`、`HAL_Init`、FreeRTOS 等）判定为裸机目标。

### 7.4 Keil MDK（`.uvprojx`）

解析 XML 中的 `<IncludePath>`（分号分隔）与 `<Define>`（逗号分隔）。

### 7.5 完全没有构建文件

退化为**目录扫描**：把所有含头文件的目录作为候选 include 路径（优先 `include` / `inc` /
`api` 等常见命名，最多 24 个）。对算法库、单文件库这类工程通常足够。

### 7.6 只想分析子目录

```bash
python -m ckg build D:/bigproject/src/core
```

或在大工程配置里用 `excludes` / `include_globs` 限定范围。

## 8. 把图谱用起来

### 8.1 命令行查询

```bash
python -m ckg query buffer_write -d D:/out/mygraph
```

```
========================================================================
FUNCTION  buffer_write   [src/buffer.c:24]
  signature: int buffer_write(buffer_t *buf, const uint8_t *data, size_t len)
  return_type: int
  metrics: {'lines': 22, 'branches': 3, 'cyclomatic': 4, 'calls': 2}
  -> HAS_PARAMETER  PARAMETER  buf
  -> HAS_VARIABLE   LOCAL      written
  -> WRITES         FIELD      tail
  -> READS          FIELD      data
  -> CALLS          FUNCTION   buffer_pending
  <- CALLS          FUNCTION   main
```

### 8.2 用 Python 直接分析 JSON

```python
import json

nodes = {n["id"]: n for n in json.load(open("ckg-out/entity.json", encoding="utf-8"))}
rels = json.load(open("ckg-out/relation.json", encoding="utf-8"))

# 谁在写全局变量 g_state？
for r in rels:
    if r["type"] == "WRITES" and nodes[r["tail"]]["name"] == "g_state":
        print(nodes[r["head"]]["name"], r.get("sites"))

# 宏 unit 影响了哪些函数？
for r in rels:
    if r["type"] == "USES_MACRO" and nodes[r["tail"]]["name"] == "unit":
        print(nodes[r["head"]]["name"])
```

### 8.3 导入图数据库 / 图工具

- **Gephi / yEd**：直接打开 `graph.graphml`。
- **Neo4j**：把两个 JSON 转成 Cypher 导入：

```python
import json
nodes = json.load(open("ckg-out/entity.json", encoding="utf-8"))
rels = json.load(open("ckg-out/relation.json", encoding="utf-8"))
with open("import.cypher", "w", encoding="utf-8") as fh:
    for n in nodes:
        fh.write(f'CREATE (:{n["type"]} {{id:"{n["id"]}", name:"{n["name"]}", '
                 f'file:"{n.get("file","")}", line:{n.get("line") or 0}}});\n')
    for r in rels:
        fh.write(f'MATCH (a {{id:"{r["head"]}"}}), (b {{id:"{r["tail"]}"}}) '
                 f'CREATE (a)-[:{r["type"]}]->(b);\n')
```

### 8.4 持续集成

把图谱生成挂到 CI 上，用 `graph_stats.json` 做质量门禁，例如：
"跨文件调用数不得下降"、"不允许出现新的 degraded 文件"。

## 9. 当成 Python 库调用

### 9.1 最简入口

```python
from ckg.pipeline import build_from_path

result = build_from_path(
    r"D:/work/myproject",
    output_dir=r"D:/out/mygraph",
    jobs=4,
)
print(result["graph"])          # {'entities': 4821, 'relations': 15302, ...}
print(result["parse_quality"])  # 逐文件解析质量
```

### 9.2 分步使用

```python
from ckg import ProjectConfig, KnowledgeGraph
from ckg.toolchain import Toolchain
from ckg.argbuilder import ArgBuilder
from ckg.extract_clang import ClangExtractor
from ckg.clang_capi import Clang

config = ProjectConfig(
    source_root=r"D:/work/myproject",
    output_dir=r"D:/out/mygraph",
    include_dirs=[r"D:/work/myproject/inc"],
    std="gnu11",
    target="arm-none-eabi",
)

toolchain = Toolchain(config)
toolchain.write_compat_header(config.output_dir)
builder = ArgBuilder(config, toolchain)

graph = KnowledgeGraph()
extractor = ClangExtractor(graph, config, args_builder=builder)
sources, headers = config.discover_sources()
extractor.run(Clang.instance(), sources, [])

print(len(graph.nodes), len(graph.edges))
for edge in list(graph.edges.values())[:5]:
    print(graph.nodes[edge["head"]]["name"], edge["type"], graph.nodes[edge["tail"]]["name"])
```

### 9.3 只取宏定义信息

```python
from ckg.macro_engine import parse_define, MacroExpander

lines = open("inc/math_utils.h", encoding="utf-8").read().splitlines()
name, is_fn_like, params, body, raw = parse_define(lines, 42, 9)
print(name, params, raw)
```

## 10. 常见问题排查

**Q1：报 `fatal error: 'xxx.h' file not found`**

默认会自动生成桩。希望它真正被找到，就把该头文件所在目录加进 `include_dirs`。
想看清到底缺什么，用 `--no-repair` 跑一次。

**Q2：报 `typedef redefinition with different types`**

目标平台判断错了。裸机工程显式写 `"target": "arm-none-eabi"`；托管工程不要启用标准库桩
（托管目标下 `std_shim_dirs` 会被自动禁用，若仍冲突就清空该字段）。

**Q3：C++ 工程报 libc++ 相关错误**

工具默认注入 `_toolchain/frontend_compat.h` 垫片。若仍失败：用 `clang_driver` 指向与工程
一致的编译器，或让 `--engine clang+treesitter` 的语法层尽量兜底。

**Q4：某个文件出来的实体明显不对**

看 `run_meta.json → parse_quality.files[<文件>]`。`degraded` 说明该文件错误较多
（通常是缺关键头文件，或用了不支持的编译器扩展）。补齐后重跑即可。

**Q5：解析很慢**

`-j N` 提高并行度；用 `excludes` 去掉第三方目录；`--no-preprocess` 跳过 `clang -E`
（会失去"真实预处理后的代码"这一层）；`--engine clang` 跳过语法层校验。

**Q6：节点太多 / 太少**

- 太多：系统头文件的符号默认已折叠（只保留被工程引用到的）。可再用 `excludes` 排除目录。
- 太少：检查 `include_globs` / `extensions` 是否限制了范围，以及 `target` 是否判断错误
  导致大量文件被跳过。

**Q7：怎么确认结果可信？**

三个信号：`diagnostics_summary.errors == 0`、`parse_quality.degraded_count == 0`、
`insights.auto_generated` 为空或很少。仓库自带 `tools/validate.py`，用 5 个不同形态的工程
做断言测试，改完代码跑一遍即可回归。
