# 解析算法详解

本文说明 code-kg 的解析算法是怎么工作的、每一步在代码里的位置、以及为什么这么做。

---

## 0. 全景流程

```
  项目目录 ──► 1 autoconfig  构建系统识别
                     │
                     ▼
               2 toolchain  编译器探测（clang -E -v / -cc1）
                     │
                     ▼
               3 shimgen    诊断驱动修复  ←── 多轮迭代
                     │
        ┌────────────┴────────────┐
        ▼                         ▼
   4 extract_clang            7 extract_treesitter
     clang 语义 AST             文本语法树（交叉校验 / 兜底）
        │                         │
        ▼                         ▼
   5 macro_engine             6 preprocess
     宏展开三层信息              clang -E + 行号映射
        └────────────┬────────────┘
                     ▼
              8 graph_builder + 可视化
```

对应代码：`ckg/pipeline.py` 的 `Pipeline.run()` 串起全部阶段。

## 1. 构建系统识别（`ckg/autoconfig.py`）

目标：**不要求用户写任何编译参数**。

### 1.1 语言盘点

先遍历目录（跳过 `.git`、`node_modules`、`build` 等），按扩展名归类，
产出语言直方图（`ckg/languages.py` 维护扩展名 ↔ 语言映射）。

### 1.2 Provider 优先级

`detect()` 按固定优先级依次尝试，先命中者胜：

| 优先级 | Provider | 触发条件 | 提取内容 |
| --- | --- | --- | --- |
| 1 | `compile_commands` | 根目录 / `build/` / 任意一级子目录下的 `compile_commands.json` | 每个文件的原始编译参数（最准确） |
| 2 | `cmake` | `CMakeLists.txt` | `include_directories`、`target_include_directories`、`add_definitions`、`target_compile_definitions`、`CMAKE_C(XX)_STANDARD` |
| 3 | `make` | `Makefile` / `makefile` / `GNUmakefile` | 汇总 `CFLAGS`/`CXXFLAGS`/`CPPFLAGS`/`INCLUDES` 等变量中的 `-I`、`-D`、`-std=` |
| 4 | `meson` | `meson.build` | `include_directories(...)`、`add_project_arguments(...)` |
| 5 | `iar` | `*.ewp` / `*.ewd` / `*.eww` | `<name>*IncludePath*</name>` 后的 `<state>` 路径列表、`*Defines*` 后的宏；处理 `$PROJ_DIR$` |
| 6 | `keil` | `*.uvprojx` / `*.uvproj` | XML 里的 `<IncludePath>`（分号分隔）、`<Define>`（逗号分隔） |
| 7 | `scan` | 以上都没有 | 含头文件的目录作为候选（`include`/`inc`/`api` 等命名加权，按深度惩罚，最多 24 个） |

### 1.3 裸机判定

单独一轮扫描，命中任意条件即判定为 embedded，并把默认 target 设为 `arm-none-eabi`：

**文件名特征**：`.ewp` `.uvprojx` `.icf` `.sct` `.ld` `.lds` `startup_` `FreeRTOSConfig.h`

**源码文本特征**（扫描前 120 个源码文件的头部 60 KB）：
`__ICCARM__` `__IAR_SYSTEMS_ICC__` `__CC_ARM` `__ARMCC_VERSION` `__arm__`
`IRQHandler` `NVIC_` `LL_` `HAL_Init` `FreeRTOS` `__irq` `__no_init` `#pragma vector`

判定结果会影响后续的类型宽度与头文件选择（见 §2.4）。

## 2. 编译器工具链探测（`ckg/toolchain.py`）

目标：**让 libclang 拥有和真实构建相同的头文件环境与预定义宏**。
libclang 本身不带你工程用的头文件，硬编码 include 路径又不可移植，所以改成"问编译器"。

### 2.1 驱动选择

```
配置里的 clang_driver  →  PATH 中的 clang  →  PATH 中的 gcc  →  python -m ziglang cc
```

找到的驱动同时用于：`probe()` 探测头文件与宏（解析用）、`Preprocessor` 跑真实 `-E`。

### 2.2 探测算法

对一个临时文件执行：

```
<driver> -E -v [-target <triple>] -x <lang> probe.c
```

捕获 stdout+stderr 后做两种解析：

**(a) 搜索路径块**

```
#include <...> search starts here:
 .../ziglang/lib/include
 .../ziglang/lib/libc/include/any-windows-any
End of search list.
```

取块内所有仍是真实目录的行，转为绝对路径 —— 这是最稳的方式，兼容 clang 与 GCC 的所有版本。

**(b) `-cc1` 命令行**

```
"..." -cc1 -triple x86_64-unknown-windows-gnu ... -D _WIN32_WINNT=0x0a00
    -isystem "..." -isystem "..." ...
```

用正则把 `-D<macro>`（以及 `-U`）/ `-isystem` / `-triple` 抽出来；
`-isystem` 与 (a) 的结果合并去重，因为 `-cc1` 行有时包含搜索块未列出的内部路径。

整个过程不执行编译器前端，耗时约 0.2 秒，结果按 `(语言, target)` 缓存。

### 2.3 参数回放（`ckg/argbuilder.py`）

每个翻译单元的 clang 命令行按如下顺序拼装（顺序即优先级）：

```
-x <lang>                       语言
-std=<std>                      标准
-D<宏>                          工程配置的宏
-I <工程 include 目录>           autoconfig 探测到的
-I <标准库桩>                    仅在非托管目标下加入（见 2.4）
-I <工程桩目录>                  用户提供的厂商头文件桩
-I <_auto_shim> -include <自动生成的声明>
-target <triple> -D... -isystem ...    ← toolchain.probe() 的全部输出
-include <_toolchain/frontend_compat.h>
-ferror-limit=0 -Wno-everything -Wno-implicit-function-declaration
```

如果 `compile_commands.json` 里有该文件的记录，则**以它为主**：先剔除
`-c` / `-o` / `-MF` / `-MT` / `-MD` 等只与编译动作相关的参数，把相对 include 路径
按记录中的 `directory` 转成绝对路径，再叠加桩目录与鲁棒性开关。

### 2.4 托管 / 裸机分流

```python
def is_hosted(language, target) -> bool:
    # 在探测到的 include 目录里能否找到 stdio.h / stdlib.h / string.h
```

- **托管目标**（Linux/Windows/macOS）：用工具链自带的真实 libc/libc++，
  自写的标准库桩会被**自动禁用**，避免 `size_t`、`intptr_t` 之类的重定义冲突。
- **裸机目标**（`arm-none-eabi` 等）：工具链没有 C 库，此时启用 `ckg/shims/`
  里的最小标准库桩，保证 `stdint.h` / `stdbool.h` / `stddef.h` / `string.h` / `math.h` 可用。

### 2.5 两个必须踩过的坑

**坑 1：libclang 的默认三元组是 MSVC 风格。**
Windows 上如果不显式指定 target，libclang 会预定义 `size_t` 为 `unsigned long long`，
与工程或桩头文件的定义冲突，报 `typedef redefinition with different types`。
算法上强制把探测到的 `-triple` 显式回传给解析器（`parser_args()` 里的 `resolved_target`）。

**坑 2：C++ 头文件版本可能比前端新。**
例如 libclang 18 解析 libc++ 19 的头文件，会缺 `__builtin_clzg` 与 `_LIBCPP_HARDENING_MODE`；
裸机目标还常缺 `__INT32_C` 系列宏。解决方式是在输出目录生成
`_toolchain/frontend_compat.h` 并**强制 include**：

```c
#ifndef __INT8_C
#define __INT8_C(c) c          /* 裸机目标通常缺这些 */
/* ... __UINT64_C(c) c##ULL */
#endif
#ifndef _LIBCPP_HARDENING_MODE
#define _LIBCPP_HARDENING_MODE _LIBCPP_HARDENING_MODE_NONE
#endif
#if defined(__clang__) && __clang_major__ < 19
#define __builtin_clzg(x, ...) __ckg_clzg_impl((unsigned long long)(x), 64)
#define __builtin_ctzg(x, ...) __ckg_ctzg_impl((unsigned long long)(x), 64)
#endif
```

这样"旧前端 + 新头文件"也能解析通过，实测让一个 C++ 工程的诊断从 44 条降到 0 条。

## 3. 诊断驱动的自动修复（`ckg/shimgen.py`）

目标：**缺 SDK、缺生成文件、缺工具链头文件时，仍然产出尽可能完整的图谱**。

### 3.1 迭代结构

```
for round in 1..4:
    对每个源文件解析一次 → 收集诊断 → 用规则匹配 → 生成修补
    如果这一轮没有任何新增 → 停止
```

关键细节：**第 1 轮用 `SkipFunctionBodies` 只解析声明部分**（快速拿到缺失头文件与未知类型），
**第 2 轮起解析完整函数体**（才能发现函数体里用到的未声明标识符）。
因此提前退出条件必须写成 `round_index >= 1 and 无新增`，否则第 1 轮空转就会误判收敛。

### 3.2 规则表

| clang 诊断 | 生成内容 |
| --- | --- |
| `'x.h' file not found` | 在 `_auto_shim/` 下生成带 include guard 的**空桩头文件**（支持子目录） |
| `unknown type name 'T'` | `typedef int T;` |
| `implicit declaration of function 'f'` / `call to undeclared function 'f'` | `int f();` |
| `use of undeclared identifier 'V'` | `extern int V;` |
| 上述 `V` 触发 `not an integer constant expression` | 撤回 `extern`，改为 `#define V 0` |

所有合成声明集中写入 `_auto_shim/ckg_autodefs.h`，通过 `-include` 强制注入每个翻译单元 ——
这样不需要修改用户的任何源码。

### 3.3 安全阀

- 合成符号总数上限 `MAX_SYNTHETIC = 600`，轮数上限 `MAX_ROUNDS = 4`；
- 桩头文件名做路径穿越校验，拒绝 `..`；
- 所有合成内容带 `auto-generated by code-kg` 注释，重跑时可被人工替换；
- 图谱中这类符号可追踪（`auto_generated`），报告中单列。

## 4. clang 语义抽取（`ckg/extract_clang.py`）

这是核心算法，目标是产出**变量级**的实体与关系。

### 4.1 libclang 绑定（`ckg/clang_capi.py`）

官方 `clang.cindex` 没暴露几个关键 API，因此用 ctypes 直接绑定 C API：

| API | 用途 |
| --- | --- |
| `clang_visitChildren` + `CXChildVisit_Recurse` | 一次调用完成整棵 AST 的深度优先遍历 |
| `clang_Cursor_isMacroFunctionLike` | 区分对象宏 / 函数宏 |
| `clang_getSpellingLocation` / `clang_getExpansionLocation` | **位置双视图**（见 4.6） |
| `clang_getCursorReferenced` | 标识符 → 定义，调用图与数据流的根基 |
| `clang_getTypeDeclaration` / `clang_getCanonicalType` | 类型解析与 typedef 展开 |
| `clang_tokenize` / `clang_getToken*` | 宏体与实参的 token 级处理 |
| `clang_getInclusions` | include 图 |

### 4.2 遍历算法：一次回调拿到祖先链

朴素实现会为每个节点再调用一次 `clang_visitChildren` 找子节点，导致 O(N) 次跨语言调用。
这里用 `CXChildVisit_Recurse` 让 clang 自己递归，回调签名自带 `parent` 游标，
再维护一个"游标键栈"还原祖先链：

```python
def _cb(cursor, parent, _data):
    pkey = cursor_key(parent)
    while len(path_keys) > 1 and path_keys[-1] != pkey:
        path_keys.pop(); path.pop()          # 回溯到真正的父节点
    visit(cursor, parent, path)              # 回调里能拿到完整祖先链
    path.append(cursor); path_keys.append(cursor_key(cursor))
    return CXChildVisit_Recurse
```

游标键 `cursor_key(cursor) = (kind, xdata, data[0], data[1], data[2])`。
注意**必须**返回 `CXChildVisit_Recurse`：返回 `Continue` 只会遍历第一层，
表现为"只有顶层声明、没有任何函数体内容"。

另外，回调内抛异常不会中断 C 侧遍历，只会被静默吞掉，因此 `walk()` 把 `visit`
包在 try/except 里并累计错误，避免调试时"什么都没发生"。

### 4.3 实体识别

| CXCursorKind | 图谱实体 |
| --- | --- |
| `FUNCTION_DECL` / `FUNCTION_TEMPLATE` | `FUNCTION` |
| `CXX_METHOD` / `CONSTRUCTOR` / `DESTRUCTOR` / `CONVERSION_FUNCTION` | `METHOD` |
| `STRUCT_DECL` / `UNION_DECL` / `CLASS_DECL` / `CLASS_TEMPLATE` | `STRUCT` / `UNION` / `CLASS` |
| `ENUM_DECL` / `ENUM_CONSTANT_DECL` | `ENUM` / `ENUM_CONST` |
| `TYPEDEF_DECL` / `TYPE_ALIAS_DECL` | `TYPEDEF` |
| `NAMESPACE` / `NAMESPACE_ALIAS` | `NAMESPACE` |
| `VAR_DECL` | 作用域内有函数 → `LOCAL`，否则 `VARIABLE` |
| `PARM_DECL` | `PARAMETER` |
| `FIELD_DECL` | `FIELD` |
| `MACRO_DEFINITION` | `MACRO` |

**节点 ID 用 USR**（`clang_getCursorUSR`）：它是 clang 的跨翻译单元稳定标识，
因此"头文件里的声明"与"源文件里的定义"会合并成同一个节点。
无 USR 的实体（宏、匿名类型）用 `{类型}:{名字}@{文件}:{行}` 兜底。

### 4.4 位置与作用域归属

`_owner(path)` 取祖先链上最近的"已登记实体"，于是：

- 顶层实体 → 归属 `FILE` 节点（`CONTAINS`）；
- 函数内变量 → 归属该函数（`HAS_VARIABLE`）；
- 结构体内字段 → 归属该结构体（`HAS_MEMBER`）；
- 类内方法 → 归属该类（`HAS_METHOD`，含类外定义的 `void Cls::f()`）。

### 4.5 读 / 写的判定算法

数据流的关键是判断标识符出现在"读"还是"写"位置。做法是把
**标识符与操作符的字节偏移量**做比较：

```
遍历祖先链，找到最近的 BinaryOperator / CompoundAssignmentOperator / UnaryOperator
  BinaryOperator 且操作符是 '='
        标识符偏移 < 操作符偏移  → WRITE
        否则                     → READ
  CompoundAssignment('+=', ...)  → READ + WRITE
  UnaryOperator '++' / '--'      → READ + WRITE（前缀与后缀都要判断）
  UnaryOperator '*' 且该表达式是赋值左侧 → WRITE（*p = v）
  其他                           → READ
```

两个容易错的细节：

1. `x++` 的操作符是**最后一个** token，`++x` 是第一个，`_unop_token()` 两者都看；
2. 遇到 `CallExpr` / `ReturnStmt` / `IfStmt` 等边界要停止上溯，否则会把
   `a = f(b)` 中的 `b` 误判成写。

操作符 token 与偏移按游标键缓存（`_binop_cache`），避免重复 tokenize。

### 4.6 宏产生的声明：位置双视图

clang 对同一个游标提供两种位置：

- **展开位置**（expansion）：源码里你写下这个名字的地方；
- **拼写位置**（spelling）：这个名字文本真正所在的位置（即宏体里）。

两者不一致 ⇒ 这个实体是**宏展开出来的**。据此：

1. 给实体打 `is_macro_generated`，并记录 `macro_spelling_site`；
2. 在宏定义区间表里反查具体是哪个宏，产出 `MACRO -GENERATES-> 实体` 边。

同理 `_via_macro()` 除了看双视图，还用**展开点的列区间**做兜底（某些 libclang 版本
对宏内标识符会返回相同的两个位置），因此 `unit.speed = v` 这类写法能稳定标出
`via_macro: unit`。

### 4.7 调用与函数指针

```
CallExpr → clang_getCursorReferenced
    FunctionDecl / Method / Template   → CALLS
    VarDecl（函数指针变量）            → CALLS_PTR
    FieldDecl（函数指针字段）          → CALLS_PTR   （dev->init()）
    无法解析且位于宏展开中             → CALLS_MACRO
```

之后做一轮**间接调用解析**：任何记录在案的 `holder -ASSIGNED_TO-> 函数`
（holder 可以是变量、字段、数组元素），都会把"调用 holder"的函数补上一条 `CALLS` 边，
并标注 `resolved_via: "function-pointer"`。这让下面这种表驱动写法能被还原：

```c
dev->init = DISPATCH(usb);   /* 宏展开为 handler_usb */
...
dev->init();                 /* 解析出 call_init -> handler_usb */
```

**赋值目标识别**：`dev->init = handler` 有两个候选左值（字段 `init` 和基变量 `dev`），
算法用优先级（成员表达式 2 > 普通标识符 1）保证记在字段上。

### 4.8 只对"工程内文件"建实体

一个 `#include <vector>` 能牵进 600 个库头文件。算法区分两类文件：

- **相关文件**（工程目录 + 配置的 include/shim 目录）：其中的声明都建实体；
- **系统 / SDK 文件**：只有被工程代码**引用到**才建节点（标 `external: true`），
  include 依赖改记成源文件上的 `system_headers: N` 计数。

同一条规则也作用在宏定义与宏展开点上，避免 libc++ 内部宏污染图谱。

## 5. 宏展开引擎（`ckg/macro_engine.py`）

产出三层信息，互相印证。

### 5.1 第一层：宏定义

libclang 对**对象宏只返回名字**作为 extent，拿不到宏体，因此算法改为**从源码文本重读**：

```
read_define_text(lines, line, column)
    → 从宏名所在列开始，处理反斜杠续行，拼成一行
parse_define(...)
    → 去注释 → 重新分词 → 拆出 (名字, 是否函数宏, 形参表, 宏体 token, 原文)
```

是否函数宏优先取 `clang_Cursor_isMacroFunctionLike()`，
回退判据是"文本里宏名后面紧跟 `(`"，避免把 `#define X (1+2)` 误判成函数宏。

### 5.2 第二层：展开点

从 clang 的详细预处理记录取每个 `MACRO_EXPANSION` 游标：

| 数据 | 来源 |
| --- | --- |
| 宏名 | `clang_getCursorSpelling` |
| 位置（文件:行:列） | `clang_getExpansionLocation` |
| 实参 | tokenize 展开点 extent，按括号深度切分逗号 |
| 完整写法 `MAX(a, BUF_SIZE)` | 拼接 token |

### 5.3 第三层：展开文本

`MacroExpander` 做 token 级递归展开：

```
expand(tokens, active, depth):
    遇到标识符且是已知宏且不在 active 中：
        函数宏且后面跟 '('  → 解析实参 → _substitute() 代入形参 → 递归展开
        对象宏               → 递归展开宏体
    否则原样输出
    保护：active 集合防自递归、depth ≤ 40、token 数 ≤ 4000
```

`_substitute()` 还处理两个预处理运算符：

- `#param` → 生成字符串字面量；
- `a ## b` → 拼接 token（宏生成函数名、`handler_##usb` 这类写法的关键）。

于是 `ABS(value)` 能算出 `(((value) < 0.0f) ? -(value) : (value))`。

### 5.4 跨翻译单元归并后的收尾

`finalize_macros()` 在所有 TU 合并后跑一次，负责：

- `MACRO_DEPENDS_ON`：宏体里引用了哪些其它宏；
- `MACRO_ALIAS`：宏体就是一个宏名；
- `USES_MACRO`：把每个展开点连到**所属函数**（展开点在 AST 里常挂在该 TU 顶层，
  所以用"函数定义的行区间包含该行号"来归属，取区间最小的那个函数）；
- `GENERATES`：宏展开产生声明的反查；
- `CALLS`：函数指针推导出的调用。

## 6. 真实预处理与死代码检测（`ckg/preprocess.py`）

### 6.1 执行

对每个 `.c` / `.cpp` 跑一次 `<driver> -E`（用与解析完全相同的 include / 宏 / target 参数），
输出保存为 `preprocessed/<name>.i`。

### 6.2 行号映射

预处理输出里的 `# <行号> "<文件>"` 标记构成一个分段线性映射：

```
markers = [(输出行, 文件, 源行), ...]     按输出顺序
对第 i 个标记：段覆盖 源行 [src_i, src_i + (out_{i+1} - out_i - 1)]
查询 (文件, 行) → 二分找到覆盖该行的段 → 求输出行 → 取该行文本
```

有了它，图谱里**任意实体或展开点**都能查到"编译时它变成了什么"。

### 6.3 顺带得到死代码检测

`#if 0` 里的代码不会产生任何标记，因此"源文件某一行没有被任何段覆盖"
就等价于"这一行没有被编译"：

```python
coverage(rel_file, line) -> bool     # 该行是否有预处理输出覆盖
```

tree-sitter 找到、而 `coverage()` 判定为未编译的实体，标记为
`dead_code: true`（可视化里画成红色虚线圈）。

---

## 7. tree-sitter 交叉校验（`ckg/extract_treesitter.py`）

第二引擎只读文本、不做预处理，作用是三件事：

1. **发现 clang 看不见的代码**：`#if 0`、未启用分支里的函数与变量；
2. **兜底**：clang 完全无法解析的文件，仍能给出基础结构；
3. **覆盖率对照**：`ts_calls_resolved` / `ts_calls_new` 量化两引擎的一致性。

合入策略（`merge_into_graph`）：

```
若 (实体类型, 名字) 已存在于 clang 结果  → 跳过（避免声明/定义重复）
否则若该行被预处理覆盖                    → 标 unmatched_by_clang（值得人工确认）
否则                                     → 标 dead_code / not_in_compiled_ast
```

## 8. 并行、图结构与导出

### 8.1 并行（`ckg/parallel_extract.py`）

libclang 的每个翻译单元相互独立，但 `CXIndex` 不是线程安全的。算法：
**每个线程一个 `CXIndex`**（`Clang.thread_index()` 用 `threading.local` 实现），
线程池按文件并行；每个 worker 产出纯数据（节点 / 边 / 宏定义 / 展开点 / 诊断），
主线程用 `KnowledgeGraph.merge()` 合并，最后统一做宏收尾。

这样既不重复加载 DLL，也避免多进程在 Windows 上的启动开销。

### 8.2 图结构（`ckg/graph_builder.py`）

```python
nodes: {node_id: {...}}                  # 按 id 去重合并
edges: {(head, rel, tail): {...}}        # 去重 + count 累计 + sites 列表
```

合并语义是算法的一部分：

- 布尔字段（`is_definition` / `external` / `dead_code`）**只增不减**；
- `expansion_count` 累加；
- `sites` / `arguments` 去重后**打平**存放。这是踩过的真实坑：多轮
  post-process 时，若把已有列表再 append 进自身，会形成自引用列表，
  导出 JSON 时报 `Circular reference detected`。

### 8.3 导出与可视化

- `entity.json` / `relation.json`：稳定排序后输出，便于 diff；
- `graph.graphml`：Gephi / yEd 可直接打开；
- `ckg.html`：自包含单文件。渲染是 Canvas 2D + **Barnes-Hut 四叉树**力导向，
  上千节点也能流畅交互；界面把 `via_macro`、`dead_code`、
  `expanded_code`（预处理后的真实代码）都做成了可视化。

## 9. 性能实测（10 个翻译单元 / 约 300 KB 源码）

| 阶段 | 耗时 |
| --- | --- |
| 工具链探测 | 0.3 s（缓存后 ≈0） |
| 自动修复（3 轮） | 4.5 s |
| clang 语义抽取（4 线程） | 15.4 s |
| `clang -E` 预处理 | 3.4 s |
| tree-sitter 校验 | 0.1 s |
| 导出 + 可视化 + 报告 | 1.2 s |
| **合计** | **≈25 s** |

主要成本在 libclang 的 Python 回调与 tokenize。已做的优化：

- token 位置按需获取（默认只算字节偏移，不算文件名与行列，省掉约 60% 的 ctypes 调用）；
- 操作符 token 与偏移按游标缓存；
- 函数签名改用类型 API 重建，不再 tokenize 整个函数体（这一项把总时间从 42 s 降到 25 s）；
- 只对相关文件建实体。

## 10. 已知限制

| 限制 | 说明 | 规避 |
| --- | --- | --- |
| 不执行代码 | 虚函数动态分发、运行时构造的回调表无法静态确定 | 看 `CALLS_PTR` 与 `ASSIGNED_TO` 候选集 |
| 宏的 token 展开不等于编译器 | 极端情况（`__VA_ARGS__` 深嵌套、宏生成 `#include`）可能不准 | 以 `clang -E` 的 `.i` 作为权威结果对照 |
| 严重残缺文件 | 缺关键类型定义时会产生连锁错误 | 看 `quality: degraded` 与 `low_confidence` 标记 |
| 非 C 系语言 | 前端绑定 clang | 可扩展 tree-sitter 引擎（见扩展指南） |
| 模板实例化 | 每个实例化可能各成一个节点 | 按 USR 合并同名，必要时在可视化里过滤 |
